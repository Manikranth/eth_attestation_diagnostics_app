▸ what does each column mean? (plain-English legend)

INFORMATION — what happened

slot block
did a block actually land at your duty slot. This is block availability, not whether your attestation was included.
exec block# / current head#
the duty-slot block's execution number, and the execution block corresponding to the node's head at the slot tick.
duty root / voted head / canon head
the canonical block root at your duty slot, the head root your validator actually voted for, and the finalized canonical head root used for the verdict.
block size / blob size
serialized beacon block bytes, and total blob-sidecar payload bytes for that duty-slot block.
head lag
how many slots behind your duty slot the block you voted for was. 0 is ideal.
head / tgt / src
were your head, target and source votes correct. – means unknown — the node was still syncing, so we don't guess (this is the fix for the old false ✓).
att on chain / incl slot / incl root / incl exec# / dist
whether your vote was found in an on-chain aggregate, which canonical block included it, that block's execution number, and how far after your duty slot that was (1 = ideal).
missed
your attestation never made it on chain.
head@tick / behind / sync
your node's health at the slot: its head slot, how far behind, and sync state.

ATTESTATION — the pipeline, in the order it happened

Every timing column shows two numbers: offset (duration) — how far into the 12s slot window the step happened, then how long that step took. A – means that half isn't available. Tagged BN (beacon node), EL (execution layer) or VC (validator client). BN consensus / EL verify / block import / head import come from Lighthouse's On-time/Delayed head block breakdown (populated once the indexer + vector run against a synced node).

Block available / Block arrival
when the block was fully available for attesting, and when it first arrived + was verified on gossip (with how late it was).
block proc
how long the node actually spent processing the block = consensus + EL verify + import-write + set-as-head (the four are broken out under VERIFY + IMPORT). Node CPU/disk time — excludes network propagation and blob wait. Over ~1s is slow. Blank for range-synced blocks (only logged at head). Lighthouse does not log a finer per-substep split; those exist only as fleet-aggregate Prometheus histograms.
blob src
slot-level blob/data-column evidence: gossip, el (getBlobs from execution), gossip+el when both appear for the slot, or none.
blob arrival / fetch·exp / cols / blob verify
first blob seen (offset), blobs served/expected by the EL, columns held via the EL, and when all data was verified + available.
BN consensus / EL verify
the consensus and execution-layer verification durations — the two biggest components of block proc. Logged on every head block; blank only for range-synced blocks.
block import / head import
block written into fork choice, then set as head (offset into slot, with the write / set-as-head durations).
VC att start / sign + pub
when the VC began producing, and how long produce+sign+publish took.
bottleneck
the slowest step this slot.

AGGREGATION — did an aggregator carry your vote

block on subnet
– — when the block/attestation first arrived on the gossip subnet needs a p2p sentry (deferred).
in agg / picked
your vote was included in an on-chain aggregate; and whether an aggregator picked it up on gossip (live p2p watcher).
cmts / pos
your committee index and position within that committee for this duty.
agg bits
how many validators were in the aggregate that carried your vote / committee size.
agg pub
when our node published its aggregate (only if this validator was an aggregator).
peer
node-wide peer count at the slot (a proxy — not a true per-aggregation count).
Δ blk
n/a — the delta between the block the aggregator saw and the block you attested needs a p2p sentry (deferred to a later phase).

PROPAGATION — how your vote spread

propag
time from slot start until your vote first hit the wire (live p2p watcher).
subnet
the gossip subnet your attestation was published on.
seen by
n/a — which peer / remote attester first saw your vote needs a p2p sentry (deferred).

VERDICT

fault
one-word classification of how the slot went (perfect, included_late, wrong_head_vote, block_arrived_late, …) and, when missed, the most likely reason.
